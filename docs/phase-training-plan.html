The red box is your roadblock. Inside it: a per-second keyword hit-map (HypnosisPhaseKeywords + AnalyzerConfig + learned corpus weights), TechniqueDetector markers, position priors (phasePositionAnchors), forward-only ordering, majority-vote smoothing, and a Viterbi-style ensemble of two analyzers (selectPreferredPhases). ~3,000 lines of careful logic.

BWhy it misclassifies

Every scoring function grades itself, never reality.

Today

intrinsicQualityScore, transcriptSupportScore, ordering & coverage bonuses — all intrinsic. The optimizer (AnalyzerImprover) can only reward the analyzer for being internally tidy and well-ordered.

There is no labeled answer key anywhere in the loop, so "did it match a real trance file" is never asked.

The fix

Put a labeled answer key into the loop. Then the same optimizer — and later a trained model — chases correctness instead of self-consistency.

The thing you're missing isn't a model. It's a labeled evaluation harness.

1The shared spine

One data format + one evaluator serve every phase. Built once

Lives in the AnalyzerImprover Mac target (offline). No rework when Phase 1 becomes Phase 2.

1a · PhaseLabelSetJSON sidecar LumeLabel writes — the anchors + gray gaps
1b · PhaseEvaluatorpredicted vs labels → scorecard, graded only on anchors
1c · CorpusEvaluationRunruns all files → report + confusion matrix

Label format

// one sidecar per mp3 — gaps mean "don't grade here", not "no phase"
{
  "audioFile": "session-042.mp3",
  "duration": 1840.0,
  "anchors": [
    { "phase":"induction", "start":35,  "end":128,  "confidence":"high" },
    { "phase":"deepening", "start":170, "end":410,  "confidence":"high" },
    { "phase":"therapy",   "start":480, "end":1300 }
  ]
}

What the evaluator reports

MetricWhat it tells you
Anchor accuracyThe headline number — % of anchored seconds predicted correctly.
Confusion matrixYour real debugging tool — which phases bleed (e.g. deepening↔therapy).
Per-phase precision/recallIs one phase chronically over- or under-called?
Ordering validityDid predictions respect canonical phase order.
Boundary placementHow far into the gray zone each boundary fell — penalized only if it lands in an anchored region.
This same runner is the optimizer's fitness function and your regression dashboard — run it after any change to see if you helped or hurt.

Because the model emits a per-second probability per phase, the gray zones are exactly where probabilities are mixed — which is exactly where your light score should cross-fade between phase settings. The thing you couldn't pin down becomes the smooth transition you wanted.

3Phase 1 — Labeled config tuning Ship day one

Reuse the whole engine. Just point the optimizer at the answer key.

LumeLabelhand-label N files → PhaseLabelSets
→
AnalyzerImproversearch AnalyzerConfig + corpus weights
→
PhaseEvaluatoranchor accuracy = fitness
↻
Winning configships in the app bundle

What changes: swap the optimizer's intrinsic fitness for anchor accuracy on held-out files. The iOS runtime is untouched — it just loads smarter parameters.

Ceiling: only as good as the current hand-built scoring can express. That's why it's a stepping stone, not the destination — but it's an immediate, real correctness gain.

Viterbi over a learned transition matrix is a principled replacement for ~800 lines of hand-tuned ensemble logic — and it's the natural home for your "all signals, hybrid" answer. Trained offline on anchor regions, shipped as a .mlmodel.
