1 · Core risk: Guideline 1.1.4 + age rating

This is the issue that motivated the review — and the one greenlight cannot see.

What the feature does

The catalog curates eight directories whose content is explicitly erotic/pornographic (MC Stories, Literotica – Mind Control, HypnoTube Stories, Warp My Mind, HypnoHub, Spirals Nightclub, Nimja, r/hypnautimagery), opened in-app via SFSafariViewController. The app curates and labels these as a feature; it does not host the content.

How Apple treats it

  • 1.1.4 "Overtly sexual or pornographic material … is not allowed." Rejection is routine when a prominent, curated feature exists primarily to surface porn. Reddit/X/browsers survive because adult content isn't their purpose and isn't developer-curated. A first-party-curated list of erotic directories reads as "the app facilitates access to pornography" — the exact 1.1.4 trigger. Risk: HIGH in the public binary.
  • Unrestricted web access → top age tier. An embedded browser to arbitrary sites forces the highest age band (17+ legacy / 18+ on Apple's 2025 13·16·18 scale) regardless of curation.
  • Rating ≠ exemption. A correct 17+/18+ rating does not make curated porn allowed under 1.1.4.

2 · Genuine blocker: privacy manifest CRITICAL

No PrivacyInfo.xcprivacy exists. Required since May 2024; absence triggers ITMS-91061 at upload. App-wide, not specific to the adult sources, but blocks any submission.

Required-Reason APIs to declare:

  • NSPrivacyAccessedAPICategoryUserDefaults — broad UserDefaults/@AppStorage use, including the new @AppStorage("readingSourceAdultConfirmed") gate. Reason CA92.1 (app's own in-process data).
  • NSPrivacyAccessedAPICategoryFileTimestamp — corpus/training code. Reason C617.1 (in-container files) or DDA9.1 per actual use.

No tracking SDK is present (see §3) → NSPrivacyTracking = false, empty tracking domains.

3 · Scanner false positives do not act

  • Amplitude / ATT (1 CRITICAL + 1 WARN) — false positive: matched the word "amplitude" in audio DSP code (EngineWaveforms.swift, BinauralBeatsEngine.swift, …), not the analytics SDK. No tracking SDK integrated.
  • Insecure HTTP — spirals entry (WARN) — spirals is HTTP-only (HTTPS handshake fails, HTTP→200). It loads via SFSafariViewController, which is out-of-process and exempt from the app's ATS, so it works with no exception. Leave as-is. Do not add NSAllowsArbitraryLoads — that weakens the whole app for nothing.
  • IAP restore / placeholder / competing-platform / CFBundleDisplayName (4 WARNs) — all under .worktrees/liminal-ui/ or Tools/CorpusGenerator/.build/, not the shipping target. The run even misidentified the bundle as a .dSYM, confirming it swept build artifacts. Re-run scoped to the app to clear.

4 · Pre-submission checklist

Blocking — before any upload

  • Add PrivacyInfo.xcprivacy to the Ilumionate target: UserDefaults (CA92.1) + FileTimestamp; NSPrivacyTracking=false
  • Decide adult-sources disposition — Option A (compile-flag) recommended

Required if any adult/web access ships

  • Set Age Rating to top tier (17+ / 18+) and answer "Unrestricted Web Access = Yes"
  • Keep the one-time adult confirmation gate (mitigation, not guarantee)

Hygiene

  • Re-run greenlight scoped to the app target to clear .worktrees/.build noise
  • Confirm a Privacy Policy URL in App Store Connect (required for 17+/web-access apps)
  • If real IAP exists (ProfileSettingsView+Sections.swift imports StoreKit), ensure a Restore Purchases affordance

5 · Bottom line

For personal / sideload use nothing here blocks you — the feature is done and works. For a public App Store release, the curated adult directories are the dominant rejection risk (Guideline 1.1.4); gate them out of the Release build (Option A) and separately add the privacy manifest the app needs regardless. The remaining greenlight "criticals" are a false positive (Amplitude) and build-artifact noise.
