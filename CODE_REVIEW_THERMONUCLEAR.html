Verdict

Micro-quality is genuinely strong; macro-structure is where the debt lives.

This codebase is unusually disciplined at the line level: repository-wide scans found zero as! force casts, zero try!, ~22 force unwraps total, no ObservableObject/@Published/@StateObject, and one DispatchQueue site. Functions are mostly short, documented, and read cleanly.

The concern is structural: logic and types have accreted into a few very large files, an 11-singleton service layer creates implicit coupling the project's own guidelines argue against, and 298 print() calls stand in for real logging. Under the thermo-nuclear bar, the analyzer subsystem has a clear "decompose this first" problem with visible code-judo simplifications left on the table.

Findings are ordered by the skill's priority: structural regressions → missed simplification → spaghetti → boundaries → file size → legibility.

BLOCK B2 The 143-line build() is the spaghetti epicenter

CorpusPhaseKnowledgeBuilder.build() (~line 3326) is the longest function in the codebase by a wide margin (143 lines vs. the next analyzer function at 76). It also nests a local makeSegment helper — doing several jobs in one scope. This is the "ad-hoc logic that should move into a dedicated abstraction" pattern: extract windowing, scoring aggregation, and segment assembly into named private methods so build() reads as a sequence of intentions, not an implementation dump.

🟠 Missed simplification ("code judo")

JUDO S1 LightMoment construction is copy-pasted

In SessionGenerator+Strategies.swift (~line 171) the phase loop builds LightMoment 3+ times per segment (base, contour points, hold), each repeating the same bilateral: useBilat ? true : nil, …, color_temperature: colorTemp boilerplate. The useBilat ? true : nil idiom alone appears 3× in this one function.

Judo move: a single private factory —

func phaseMoment(at time: TimeInterval, phase: PhaseSegment,
                 progress: Double, config: GenerationConfig) -> LightMoment

collapses the call sites to moments.append(phaseMoment(...)) and makes the per-point differences (waveform swap at segDuration > 120, ramp duration) the only visible variation. Removes moving pieces rather than tidying them.

JUDO S2 Two near-identical inits on HypnosisPhaseAnalyzer

Lines 89–102: init(config: KeywordPipeline?) and init(config: AnalyzerConfig) both assign the same four stored properties. Funnel one into the other so the assignment list exists once — otherwise a new config field gets added to one initializer and forgotten in the other.

JUDO S3 Phase mapping scattered across many big switches

SessionGenerator+Strategies.swift (88 cases), HypnosisPhaseAnalyzer.swift (78), LightScorePhaseTargeting.swift (72) all switch on HypnosisMetadata.Phase. Each new phase becomes a multi-file edit. Consider moving per-phase parameters (frequency, waveform, color temp, intensity, bilateral) onto the phase as a PhaseProfile data table — one canonical lookup instead of N parallel switches.

🟡 Boundary & ownership problems

BOUND O1 Eleven singletons form an implicit service graph

static let shared on: NowPlayingState, AnalysisStateManager, PerformanceOptimizer, FolderStore, AnalysisPreferences, TranceHaptics, OrbCrashLogger, AnalysisProgressStore, CorpusPhaseKnowledgeCache, SessionHistoryManager, TrainingCorpusManager.

UnifiedPlayerViewModel alone reaches into .shared 19×; AudioLibraryView 10×; AnalysisStateManager 9×. The project's SwiftUI guidance is explicit: shared data should flow through @State ownership + @Environment/@Bindable injection, not global accessors. The tell: AnalysisStateManager already added a second init purely "for unit testing" (line 51) — the singleton is fighting testability.

Judo path: an AppEnvironment (or @Environment keys) owns these once at the app root and injects downward. Don't do all 11 at once — start with the most-touched (AnalysisStateManager, NowPlayingState, AnalysisProgressStore).

BOUND O2 WordTimestamp (shared model) lives inside the analyzer file

WordTimestamp is defined at line 26 of HypnosisPhaseAnalyzer.swift but consumed across TechniqueDetector, ChunkedPhaseAnalyzer, and SessionGenerator. A foundational shared type owned by one feature file is a canonical-ownership leak — anyone importing it inherits a 3,698-line dependency. Move it to its own file.

BOUND O3 Redundant : Sendable on a @MainActor @Observable class

AnalysisStateManager (line 25) declares explicit : Sendable on a @MainActor mutable @Observable class. @MainActor types are already implicitly Sendable; the explicit conformance on a class with mutable var state is redundant and misleading (reads as "safe to pass across actors" when safety actually comes from main-actor isolation). Drop it; sweep for the same pattern.

🟢 Legibility

LEGIB L1 298 print() calls instead of structured logging

print() appears 298 times. os.Logger is already available (OrbCrashLogger imports os) — the canonical tool exists, just unused. Top offenders: SessionValidationExample (81), AnalysisStateManager (35), AudioManager (23), AudioLibraryView+Actions (21). print in a shipping target is invisible in production, not level-filterable, and runs unconditionally on the calling thread.

LEGIB L2 SessionValidationExample.swift looks like scratch code in the app target

Self-described as "Example code… can be run from a command-line tool or in Xcode" and 81 of the 298 prints. If it's a dev utility it shouldn't be in the shipping target — move to a tools/test target or delete. Example code that ships is dead weight a reviewer keeps tripping over.

LEGIB L3 Views decomposed via computed properties, not child structs

MindMachineView and LibraryView each expose 14 var x: some View computed properties; StreamingBrowserView 12, AnalyzerView/ProfileSettingsView+Sections 11. The guideline is explicit: "do not break views up using computed properties; place them into new View structs." Computed decomposition keeps all state in one giant struct (over-invalidation) and defeats per-subview previews. These same files dominate the deep-nesting scan (MindMachineView 128 lines indented ≥24 spaces, HomeView 111) — same root cause. Extracting real View structs fixes legibility and render cost.

LEGIB L4 GeometryReader / UIScreen.main in 11 files

Guidelines steer toward containerRelativeFrame()/visualEffect() over GeometryReader, and forbid UIScreen.main.bounds. 11 files use one or the other (incl. MindMachineView, HomeView, UnifiedPlayerViewModel). Many simple proportional-sizing uses have a one-line modern replacement; UIScreen.main breaks under iPad multitasking/Stage Manager.

What's already good (don't regress it)

  • No force casts, no try!, ~22 force unwraps total across 41k lines — exceptional.
  • No legacy Observation (ObservableObject/@Published/@StateObject: 0). On @Observable + @MainActor as guidelines require.
  • One DispatchQueue site (InAppBrowserView) — the rest is async/await.
  • Functions are short and documented; analyzer content reads well. The problem is purely packaging.

Recommended sequence

  2. Move WordTimestamp to its own file (O2) as part of step 1.
  3. Split SessionGenerator+Strategies.swift and AnalyzerOptimizer.swift under 1k.
  4. Extract the LightMoment factory (S1) and merge duplicate inits (S2) — small, high-leverage.
  5. Refactor CorpusPhaseKnowledgeBuilder.build() into named steps (B2).
  6. Introduce os.Logger, retire print(), relocate/remove SessionValidationExample (L1/L2).
  7. Plan the singleton → @Environment migration (O1) — biggest testability payoff, biggest effort; sequence deliberately.
  8. Convert computed sub-views to View structs in the worst offenders (L3).
